# 流式管线逻辑梳理（基于代码事实 · 2026-09-21）

> 目的：把"素材从磁盘到 FBX"的**实际执行逻辑**与**测试逻辑**一次讲清。
> 本文以已交付代码为准（非设计稿），每一步标注：谁执行 / 何时触发 / 在哪能看到。

---

## 一、三个角色与唯一事实源

```
┌─────────────┐   提交 stream_next    ┌──────────────┐
│  UE 面板     │ ───────────────────▶ │  Python 执行器 │
│ (配置+启停+   │ ◀─────────────────── │ (扫描/队列/    │
│  绑定确认)    │   REMAINING 协议行    │  解算/导出)    │
└─────────────┘                      └──────┬───────┘
                                            │ 写
                                            ▼
                                   ┌────────────────┐
                            读 ◀─── │  磁盘文件        │
                            ┌───▶  │ (队列/状态/进度) │
                            │      └────────────────┘
                     ┌──────┴──────┐
                     │ 全局控制台    │  ← 独立看盘+读文件
                     │ (1s 刷新)    │     （面板冻结期间也能看）
                     └─────────────┘
```

**核心纪律**：一切状态以磁盘文件为准（`queue_state.json` / `stream_state.json` / `progress.json` / `stream_bindings.json`）。面板和控制台都只是**只读展示端**。

## 二、素材生命周期（状态机）

### 表演素材（最终产出 FBX 的素材）

```
① 磁盘到达        素材目录出现在 inbox/{组}/ 下
   │               谁：上环节（测试时 = 你手动从 source 复制）
   │               看点：控制台[盘] 行"已到达"（控制台直接扫盘，不依赖监听）
   ▼
② 等待就绪        拷贝中（缺 mov/bin 或 3 秒稳定期未过）
   │               谁：Scanner 轮询判定（5 秒一轮）
   │               看点：控制台"加载中（等待就绪）"；此期间【不会】被处理
   ▼
③ 等待绑定        就绪但该组无身份 → 进 pending 池（不在队列里！）
   │               谁判定：入队器查绑定表（组绑定 → 根组兜底 → 都无则等待）
   │               看点：控制台"已加载·等待身份绑定"；面板分组区"<未绑定>·待N"
   ▼
④ 排队 pending    绑定就绪 → 入队（此刻把身份"快照"到任务上，之后不再变）
   │               谁：绑定确认时冲刷 / 新素材到达时直接入队
   │               看点：控制台"已加载·待解算"；面板"待处理 N"
   ▼
⑤ 导入 importing  队头任务开始：素材转码进 UE（约 30 秒~2.5 分钟）
   │               看点：控制台[当前进度]"导入转换 [####--] 40%（预计）"
   ▼
⑥ 解算 solving    深度解算（20~35 分钟，期间【面板冻结】= 正常）
   │               看点：控制台[当前进度]每秒刷新（百分比/帧/剩余）★唯一实时窗口
   ▼
⑦ 导出 exporting  导出 AS/LS/FBX（若目标已有同名 FBX 会弹【覆写确认】——引擎行为）
   │               看点：控制台"导出中"
   ▼
⑧ 完成 done       FBX 落盘到导出路径
                   看点：控制台"已完成"列（名称+耗时+FBX）；面板"已交付 N"
```

### ID/ROM 素材（身份的原料，不产出 FBX）

```
① 到达 inbox/_id/ → ② 就绪 → ③ 入队(kind=id) → ④ 自动导入 UE（到"身份导入"目录）
→ ⑤ done。仅此而已——它只是把素材放进工程，身份【制作】仍是人工的。
```

## 三、身份生命周期（当前最容易混乱的部分）

```
① ROM 素材进 _id/ ──▶ 自动导入 UE（系统做，无需点击）
② 人工制作身份：面板[打开编辑器] → Identity 编辑器里 conform/Prepare → 存到资产目录 /Game/ID
③ 面板[确认绑定]：
     绑定目标 = 下拉选择（自动预选 = 从最新 ROM 名解析的 am/pm；未命中=(根)全部）
     身份资产 = 资产目录里最新修改的 MetaHumanIdentity（自动取）
     → 写入绑定表 {组: 身份}
     → 该组 pending 素材即刻冲刷入队
④ 此后新到素材：入队时用该身份（快照）
   同组二次绑定 = 覆盖（新素材用新身份；已入队的保持旧快照不变）
```

**绑定时机与素材到达顺序无关**（先绑定后拖素材 / 先拖素材后绑定，最终等价——素材在 pending 池等绑定）。

## 四、一次完整生产流程（时间线）

```
09:00  面板填四项配置 → [保存为默认] → [启动监听]
       控制台弹出（身份带/三列/当前进度）
09:01  上环节拷入 ROM（_id/rom_pm_002）→ 自动导入（~1 分钟）
09:05  上环节拷入第 1 条表演素材（pm/ep001）→ 等待绑定
09:10  操作员：[打开编辑器] → 制作身份 → 存 /Game/ID → [确认绑定]
       （绑定目标已自动预选 pm/ —— 来源 rom_pm_002 命名识别）
       → pending 冲刷 → ep001 开始导入+解算
09:12  上环节继续拷 ep002、ep003…（解算阻塞期到达）
       → 控制台[盘]行立即显示"已到达·等待接管"
       → 当前条解算完（~30 分钟）→ 段间补扫发现 → 自动接续
12:00  全部完成：已交付 N = 素材数，FBX 全落盘
       控制台常驻可回看（已完成的名称与耗时）
```

## 六、当前不清晰的根因（诚实清单）与改进方案

| # | 混乱点 | 根因 | 改进方案 |
|---|---|---|---|
| 1 | **"必须先启动监听"不直观**——拖素材没反应 | 扫描器在监听启动时才创建；未监听=没人看盘 | A（建议）：**启动编辑器时若未监听，面板身份区与控制台顶部持续显示醒目提示**"⚠ 未监听——素材不会被处理"。已有控制台[盘]行提示，补面板侧 |
| 2 | **pending 池概念不可见**——"队列 0 但素材明明在" | pending 是内存池，不在队列文件里 | 已修（pending_binding 注入 + 三端显示"已发现 N 等待绑定"）；**测试中请注意看这一行**，它就是答案 |
| 3 | **身份流程三实体**（ROM素材/身份资产/绑定关系）关系绕 | 语义分层正确但展示分散 | B（建议）：控制台身份带显示完整链 `ROM:xxx → 身份:yyy → 绑定:pm/`，一眼看全 |
| 4 | **解算期面板冻结**让人以为坏了 | 物理限制（游戏线程独占） | 已在控制台解决（当前进度每秒刷新+明确文案"面板冻结时此窗口照常刷新"）；面板步骤条已是极简状态 |

## 八、e011 事故分析（2026-09-21 实录 · 已修复）

### 真相时间线（日志+文件系统证据闭环）

```
10:53:20  e011（第一次拷入）被发现 → 入队 → 开始导入
10:53:39  编辑器会话结束（导入被中断，任务滞留 importing）
  ↓       期间【素材被移走】（accept3_source 里至今有它——move/cut 走了）
11:38:34  新会话恢复机制重排队 → 重试导入 → C++:"take 目录不存在"（属实）
          → Python 未拦 → 继续定位资产 → 误报"未找到已导入素材" → failed
11:50:23  素材被重新拷回（CreationTime=11:50:23 实证）
          → 但扫描器已见过该 key → 永不重新发现 → 失败三不管
11:58     控制台把它显示为"[盘] 已到达 · 未监听"（第三重误导）
```

### 三重缺陷（全部已修复）

| # | 缺陷 | 修复 | 验证 |
|---|---|---|---|
| 1 | **失败三不管**：失败素材放回后永远无人处理 | `_revive_failed()`：素材目录 mtime > 失败时刻 → 自动重新排队（mtime 判据防无限重试循环） | 5.4 专项 14 断言全过 |
| 2 | **误导性错误链**：目录不存在 → 报"未找到已导入素材" | 导入前目录预检 → 准确报"素材目录不存在（可能被移走，放回后自动重新排队）" | 6a/6b |
| 3 | **控制台误标**：失败素材不在任何展示名单 → 被 [盘] 行标为"未监听" | ① tasks_detail 增加 failed 列表 ② 控制台新增红色"已失败"区块（含原因+"放回后自动重新排队"提示）③ [盘] 行排除 failed | 契约测试更新 + 编译零错 |

### 结论：系统当时的行为全部符合设计，但设计漏了"素材中途被移走"这一场景

教训：**素材在热文件夹中不是静态的**——被移走/放回都必须收敛到一致状态。现在的语义：
素材放回（重新拷贝）= 重新参与队列；只有目录内容变化（mtime 更新）才触发复活，不会无限重试。
