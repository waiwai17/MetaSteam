# 流式面部捕捉管线 · 设计方案

> **文档基线**：2026-09-17（v2：整合四项问答更新——牙齿校准 / 积压与分配 / 三态开关 / 监控与 Auto Tab）
> **需求**：现场拍摄素材逐条同步到本地文件夹，工具侧随到随导入、随到随解算；ID 素材到达后自动/半自动制作 identity；支持上午/下午多 ID 时段切换。
> **关联文档**：`MetaHumanSolver_项目文档.md`（§5.6 实测记录、§7 变更史）

## 一、第一性原理：批处理 → 流式的范式变化

| 假设 | 批处理（现状） | 流式（新需求） |
|---|---|---|
| 数据集 | 有限、静态（discover 一次，列表固定） | 无限、增长（take 陆续到达） |
| 生命周期 | 有明确"开始/全部完成" | 只有"当前已追平"，无终点 |
| 幂等 | 防重复跑 | 同样需要 + **防"半拷贝数据被处理"** |
| 触发 | 人工点开始 | 事件驱动（数据到达） |

由流式假设推导出五个核心问题：

| # | 问题 | 结论摘要 |
|---|---|---|
| P1 | **数据完整性判定**：拷贝需要时间（take 几百 MB~GB），目录出现 ≠ 拷完 | 就绪标记文件为主（需与上环节约定）+ 静默期兜底；现有 `_is_take_dir`（看 take.json）不够 |
| P2 | **ID 制作自动化** | 官方脚本支持全链路，但有**三个坑**：云服务依赖（仅 IOA 机器可达）、neutral 选帧、牙齿校准缺失（§三） |
| P3 | **上/下午 ID 分配** | 活跃 identity 指针 + **入队时绑定**（§四）——积压不影响分配 |
| P4 | **解算积压是数学必然**：拍一条 1~3 分钟 vs 解一条 34 分钟 | 队列必然增长；目标是"随到随排、无人值守"；监控面板显示队列深度 + 预计追平时刻（§七） |
| P5 | **watcher 不需要实时，只需要不漏** | 解算是天然瓶颈，纯轮询 + 幂等 diff 足够；深度解算阻塞期间轮询"失明"没关系，下一段开始前补扫 |

## 三、Q1：ID 制作能否自动化

**官方支持全链路**（Neutral 部分）。引擎脚本
`D:/UE_5.7/Engine/Plugins/MetaHuman/MetaHumanAnimator/Content/Python/create_identity_for_performance.py`
的 `create_identity_from_frame()`：

```python
# 1. 建 identity 资产 + face part
identity = create_or_recreate_asset(MetaHumanIdentity, ...)
face = identity.get_or_create_part_of_class(MetaHumanIdentityFace)
# 2. 关联 ROM（关键 API 已确认）
pose = new_object(MetaHumanIdentityPose, outer=face)
face.add_pose_of_type(NEUTRAL, pose)
pose.set_capture_data(ROM的FootageCaptureData)
# 3. 提升帧 + 跟踪 + 拟合
pose.load_default_tracker(); frame, _ = pose.add_new_promoted_frame()
frame.frame_number = neutral_frame
identity.start_frame_tracking_pipeline(...)
face.conform()
# 4. 云端 DNA + Prepare
identity.create_dna_for_identity()          # ← Mesh to MetaHuman 云服务
# 云回调后 → face.run_predictive_solver_training()   # Prepare（已实测可跑，~10 分钟）
```

### 三个坑

| 坑 | 说明 | 对策 |
|---|---|---|
| **云服务依赖** | `create_dna_for_identity()` 走云端 AutoRig（Epic 账号 + 网络）。**本项目约束：仅挂载 IOA 的电脑可访问** | 见 §3.1 |
| **neutral 帧选择** | 脚本要求指定"中性表情帧"帧号；选错帧 → conform 质量差 → 全天解算质量差 | 拍摄约定：ID 拍摄前 3 秒保持无表情，自动取固定帧；或半自动 |
| **牙齿校准缺失** | 官方脚本**只做 Neutral，不含牙齿**（见 §3.2） | 牙齿归入半自动/人工环节，或 Spike V-W6 验证后决定 |

### 3.1 IOA 网络约束的解决方案

| 方案 | 原理 | 评估 |
|---|---|---|
| **C. ID 制作机解耦（推荐主线）** | IOA 电脑专职做 ID（一天仅 2 次：上午/下午），产出 identity 资产迁移/共享给解算机；解算机无需网络 | 零技术风险，与"解算/导出解耦"同思路；需 Spike V-W5 验证资产迁移后可用性 |
| B. 无 DNA 离线 identity | conform 后跳过云 DNA 直接 Prepare（空 identity 上实测 training 可单独跑） | 纯推测，Spike V-W4（可选，优先级低） |
| ~~A. 离线 DNA 复用~~ | ~~`create_identity_from_dna_file()`~~ | **已否决**（2026-09-17：auto_dna 不可行） |
| ~~D. 代理绕行~~ | IOA 机器做代理 | 不推荐：IOA 是安全准入系统，绕行有合规风险 |

**推荐组合**：方案 C 为主线（manual / semi 模式），IOA 机器本机可跑 auto。

### 3.2 牙齿校准（2026-09-17 勘察结论）

**引擎支持，但官方自动链路没做，Python 可调性待验证**：

| 事实 | 依据 |
|---|---|
| 引擎有牙齿机制 | `EIdentityPoseType` 枚举含 `Teeth` 值（`MetaHumanIdentityPose.h:20-27`） |
| C++ 有拟合 API | `UMetaHumanIdentityFace::CanFitTeeth()` / `FitTeeth()`（`MetaHumanIdentityParts.h:276-281`） |
| **官方脚本不含牙齿** | `create_identity_for_performance.py` 只做 NEUTRAL pose，无任何 Teeth 步骤 |
| **`FitTeeth` 疑似无 `UFUNCTION`** | 需 Spike V-W6 实测 Python 可调性；不可调则只能 C++ 侧加桥或人工 |
| 牙齿未校准不阻断流程 | `MetaHumanIdentityStateValidator.h:25` 注释："Teeth fitting...doesn't prevent you from further progressing"——可 Prepare/解算，但牙齿动画质量打折 |

**✅ T1 实测结论（2026-09-17，详见 `spike/t1_conclusion.md`）**：

- **素材链路 Python 全可用**：`IdentityPoseType.TEETH` 枚举存在、`add_pose_of_type(TEETH, pose)` 可调、pose 级 API（`set_capture_data`/`add_new_promoted_frame`/`load_default_tracker`）与 Neutral 流程完全同构——加牙齿 pose、关联露齿帧 ROM、提升帧、跟踪，全部可自动化；
- **拟合步骤 Python 缺失**：`fit_teeth()` / `can_fit_teeth()` 无 `UFUNCTION`（`dir(face)` 42 个方法中无任何 teeth 项）——牙齿网格拟合这最后一步调不到；
- **解决方案**：① C++ 桥（推荐，插件加 `MHS_FitTeeth` UFUNCTION 转发，一次编译，随 Phase 4 交付）；② semi 模式人工兜底（已就绪）；③ T4 若证明牙齿区域质量可接受则 auto 模式先不带牙齿。

## 四、Q2：上午/下午 ID 的分配管理——活跃指针 + 入队时绑定

拍摄现场的真实顺序必然有序：

```
上午ID → 上午表演们… → 下午ID → 下午表演们…
```

状态机规则（**关键设计：入队时绑定，而非解算时查指针**）：

1. 表演 take 到达 → **入队那一刻**快照绑定"当时的活跃 identity"——这条绑定关系随任务持久化，之后无论何时解算、排队多久，都不会变；
2. 新 ID 素材到达 → 导入 + 制作 + Prepare（约 10~15 分钟）→ 完成后**活跃指针切换**——**只影响之后入队的 take**；
3. **积压完全不影响分配正确性**：上午的 take 哪怕下午 3 点才轮到解算，仍用上午 ID（绑定关系在入队时已定）；
4. **pending 池**：新 ID 制作期间到达的表演暂存（下午的表演必然在下午 ID 拍完后才开拍，等待是正确归属）；**超时降级**：pending 等待超过 30 分钟仍无新 ID → 绑定旧 ID 入队 + 黄色警告（防 ID 制作失败导致永久阻塞），事后可手动重算；
5. 指针 + 队列 + 绑定关系全部**落盘持久化**（原子写：tmp + rename），崩溃重启恢复，不乱配；
6. 兜底：任何 take 配错 ID → 手动指定 identity 重算（幂等天然支持，复用 `identity_map` 语义作手动覆盖）。

> 上下午问题因此**自动消解**：不需要预知时段，指针随 ID 就绪自然推进；积压只影响"何时算完"，不影响"用哪个 ID 算"。

## 五、identity_mode 三态开关

```jsonc
// watcher 配置（job / Auto Tab）
"identity_mode": "semi",        // manual（全手动）| auto（全自动云）| semi（半自动，推荐默认）
"identity_asset_dir": "",       // manual/semi：人工确认后的 identity 资产放置处
                                //（watcher 检测到新资产即切活跃指针）
"pending_timeout_min": 30       // pending 池超时降级（分钟）
```

| 模式 | 行为 | 适用 |
|---|---|---|
| `manual` 全手动 | 检测到 ID 素材 → 仅导入 ROM + 提示；人工在 ID 制作机完成全部制作（含牙齿校准）→ 资产放 `identity_asset_dir` → watcher 检测到 → 切指针 | 无 IOA 网络的解算机 |
| `semi` 半自动（推荐） | 自动跑官方链路（Neutral + 云 DNA + Prepare）→ **人工在编辑器里过目/补牙齿校准** → 确认后资产放约定处 → 切指针 | IOA 制作机；兼顾自动化效率与质量把关 |
| `auto` 全自动 | 检测到 ID → 全链路自动（不含牙齿）→ 完成即切指针 | IOA 机器；V-W2 质量验证通过后 |

## 六、面板：新增「Auto」Tab（流式操作流）

现有三个 Tab（深度/视频/音频）都是**批处理语义**（选数据 → 开始 → 完成）。流式是不同心智模型（配置一次 → 持续监听），混在深度 Tab 里会污染批处理交互。**新增第四个 Tab「Auto」作为流式操作中心**：

```
┌─ MetaHuman Solver ───────────────────────────── ● 监听中 ─┐
│ [深度解算] [视频解算] [音频解算] [Auto ◄新增]               │
│                                                             │
│ ── 监听配置 ──────────────────────────────────────────────  │
│  热文件夹   [E:\Capture\inbox          ] [浏览]             │
│  身份模式   [半自动（推荐） ▼]   ← manual / auto / semi      │
│  ID资产目录 [/Game/IDs                ] [浏览]              │
│  导入路径   [/Game/CaptureManager/Auto] [浏览] [⟲]          │
│  输出路径   [E:\OUT\auto_fbx          ] [浏览]              │
│                                                             │
│  [停止监听]  或  [开始监听]      就绪标记: ☑ .done 文件      │
│                                                             │
│ ── 运行状态 ──────────────────────────────────────────────  │
│  活跃 ID: ID_am_0917（09:42 切换）      [历史 ▾]            │
│  ┌────────┬────────┬────────┬────────┬────────┐            │
│  │ 待导入  │ 待解算  │ 解算中 │ 已完成  │ 失败   │            │
│  │   2    │   11   │   1    │   23   │   0    │            │
│  └────────┴────────┴────────┴────────┴────────┘            │
│  预计追平: 今天 21:37（平均 34min × 剩余 12 条）             │
│                                                             │
│ ── 事件流（最近）─────────────────────────────────────────  │
│  14:02  [解算完成] Anims_ep012 ✓ 35.1min                    │
│  13:58  [新素材]   Anims_ep013 已入队（绑定 ID_am_0917）     │
│  13:41  [新素材]   ID_pm_0917 识别为 ID素材，开始制作(semi)  │
│  13:12  [解算完成] Anims_ep011 ✓ 33.8min                    │
└─────────────────────────────────────────────────────────────┘
```

**设计要点**：

1. **与批处理 Tab 完全隔离**：深度 Tab 不动，Auto Tab 独立配置（独立 job 文件 `job_auto.json`），两模式可并行（不同 capture_root）但不建议同机同时跑解算；
2. **身份模式下拉**替代散落的勾选框；semi 是推荐默认（质量可控）；
3. **队列统计卡**是核心信息（一眼看清运转健康度）；**预计追平时刻**直接回答"还要多久"；
4. **事件流**取代滚动作业日志——只显示关键事件（新素材/入队/完成/失败/ID 切换），全量日志仍走现有日志框；
5. `pending` 池有内容时在"待解算"卡上叠加黄色角标与悬停提示。

## 七、监控设计（Auto Tab 监看区 + Web 仪表盘）

流式是无终点过程 + 无人值守，监控是刚需而非锦上添花。两层设计：

### 7.1 UE 面板监看区（Auto Tab 内嵌，随 §六 交付）

数据源：`stream_state.json`（watcher/队列状态）+ 现有 `progress.json`（解算进度心跳）。

### 7.2 Web 仪表盘（跨机/手机查看，Phase 4.5，约半天）

- 纯 Python 只读 HTTP 服务（读 `stream_state.json` + `progress.json` 渲染单页）；
- 任何浏览器（含现场制片/导演的手机）可看：队列统计、活跃 ID、追平预估、最近事件；
- **不依赖 UE 运行**——与"解算/导出解耦"同思路，UE 崩了仪表盘还在；
- （可选）异常告警 webhook：ID 制作失败 / 连续解算失败 / 磁盘不足 → 推送到企业微信/钉钉。

## 十、Spike 测试计划（逐个执行，按依赖排序）

> 排序原则：先本机零依赖项（T1/T2 可立即开始）→ IOA 云链路（T3）→ 质量与迁移（T4/T5 依赖 T3 产物）。
> 每项一次通过即解锁下一项；失败则评估降级路径再继续。

| 序 | 测试 | 环境 | 内容与判据 | 预计耗时 |
|---|---|---|---|---|
| **T1** | **牙齿 API 可调性**（V-W6） | 本机编辑器 | ✅ **已完成（2026-09-17）**：素材链路全可用（TEETH pose/关联ROM/提升帧），`fit_teeth()` 无 UFUNCTION 不可调 → 方案：C++ 桥 `MHS_FitTeeth`（推荐）+ semi 兜底。详见 `spike/t1_conclusion.md` | ✅ 已完成 |

| **T3** | **官方云链路全流程**（V-W1） | **IOA 机器** | 已登录 Epic 账号前提下，跑 `create_identity_from_frame`（用已导入 ROM）。判据：conform → 云 DNA → Prepare 全通；记录各阶段耗时（预计 10~15 分钟） | 1 小时 |
| **T4** | **自动 ID 解算质量**（V-W2） | 本机（用 T3 产物） | 用自动 ID 解算 1 条表演（Preview 模式省时），与手工 ID（`/Game/ID/ID`）产物对比：FBX 曲线数、目视质量、牙齿/口腔区域动画。判据：曲线数一致 + 质量可接受 → auto 模式可用；不达标 → semi/manual 为主 | 1 小时 + 解算时长 |
| **T5** | **identity 资产跨机迁移**（V-W5） | IOA 机 → 解算机 | T3 的 identity 资产 migrate/拷贝到解算机 → `can_process()` + 解算 1 条。判据：迁移后可用 → 方案 C（ID 制作机解耦）成立，解算机免网络 | 30 分钟 + 解算 |
| T6（可选） | 无 DNA 离线 identity（V-W4） | 本机 | conform 后跳过云 DNA 直接 Prepare → 解算。判据：可行则多一条完全离线路径（优先级低，时间富余再做） | 1 小时 |

## 十一、阶段计划

```
Phase 0  与上环节谈协议（.done 标记 / ID 目录约定）           ← 立即并行
```
